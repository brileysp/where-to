01 · Diagnosis

Why "base" doesn't mean anything

The current engine assigns each of the 53 sliders to one of ten shared formulas by loose theme — wildlife covers wildlifeViewing, safari, whaleWatching, and wildflowerBlooms; culture covers auroraChasing, museumsArt, historyArchaeology, and festivals. The problem: within one theme, the sliders don't share a shape.

Ask what "base" means for museumsArt and the answer is real — a museum collection's quality doesn't have a season, so base is just the score. Ask the same question for auroraChasing and there's no honest answer, because aurora visibility isn't a quality that fluctuates around a typical value — it's on in the dark months and not a real activity at all the rest of the year. Both sliders run through the same culture formula, with the same small ±1/−2/−3 weather deltas, because that formula has to serve both cases at once.

The formula's own escape hatches are the evidence this doesn't fit: sliderEvents exists because four different formulas need "the real exception" for a genuine seasonal spike; sliderCaps exists specifically so a flat +7 wildlife-peak bonus doesn't overstate a merely-decent destination the way it does Serengeti; noSnow/inaccessible/wildlifeClosed are three separately-invented hard floors for the same underlying need ("this month is just zero"). Each was added to patch a specific destination bug — the code comments name them: reproduces the Kruger case, reproduces the Sydney bug. None of them were part of one design; they accumulated.

The empirical symptom: across all 200 destinations, 91 slider-curves swing 4 or more points above their base in a single month — the largest is +8 (a base of 2 reaching a monthly value of 10). Some of that is real (Rio's Carnival month should be a 10). Some of it is a wrong base compensated by an oversized bonus — Whistler's mountainBiking base is a 2, when the real story is a bike park that's excellent all summer and closed in winter. The formula can't tell those two cases apart, because it was never given the vocabulary to describe a shape, only a number and a set of universal nudges.

02 · The proposal

One primitive: anchors, eased into each other

Every slider curve — flat, single-peak, double-peak, sharp spike, hard cutoff — is described the same way: a sparse list of anchors (specific months with a known value), connected by a smooth, S-shaped transition whose steepness is a number you control.

Corrections, made before this reached implementation — this design went through two rounds of independent adversarial review after the first draft below. Round one found a real data-corruption bug and a real gap between what "steepness" claimed to do and what it actually did. Both are described and fixed here, not smoothed over: the earlier draft had each anchor decay independently toward a shared "baseline," picking whichever anchor was nearest for a given month — fine for one anchor, but with two or more close together it produced a discontinuity (one month could jump onto a totally different anchor's curve than its neighbor). That's replaced below by piecewise easing between consecutive anchors. Round one then found two more problems in that version, both fixed in what follows: anchors sharing a month could silently delete a third anchor from the curve, and averaging two anchors' steepness together made independent control of a peak's rise vs. its fall impossible — exactly the asymmetric-curve claim this design is supposed to deliver on.

Round two re-ran the math independently rather than trusting round one's fix, and confirmed the duplicate-month and steepness fixes were both real — but everything around them wasn't: no validation code had actually been shown, only promised in prose; a steepness below 1 silently produces a non-monotonic curve (not just "less gradual," as originally described); the interface comment and the admin table disagreed about what "gradual" steepness even means; and the crowds/deals formula wasn't precise enough to implement. All four were "fixed" with real code that round.

Round three found that "real code" isn't the same as run code: the defense-in-depth clamp only floored steepness, never capped it, so an out-of-range value could still divide 0/0 into NaN inside ease() — the exact silent-corruption failure it was written to prevent. An empty anchor list returned undefined with no guard at all. And the crowds/deals formula, never once executed against anything, turned out to degenerate into a near step-function for any destination with sparse slider coverage — the normal case, not an edge case. The response wasn't a fourth round of manual patching: the reference implementation was rewritten as real, typed TypeScript with an actual test suite, including four property-based fuzz tests generating thousands of random (and deliberately invariant-violating) anchor sets — see src/lib/scoring/curve.ts and tests/scoring/curve.test.ts.

Round four checked whether that fuzz suite actually covered the input space, rather than trusting that "fuzz-tested" meant "safe." It didn't, in two ways that are the same bug class one layer deeper: every fuzz generator randomized Anchor fields but never the query month parameter itself — which isn't part of an anchor, is never validated by the schema, and in real use would come from something like new Date().getMonth()+1. An out-of-range month either crashed on an error message that claimed the case was impossible, or silently returned an arithmetic accident for a negative month. Separately, clamp()'s use of Math.min/Math.max silently returns NaN when given NaN — the one input that footgun actually needed to guard against, and the one value none of the fuzz generators ever produced (they generated large, negative, and extreme numbers, never NaN itself). The response that round: validate the query month too, and make clamp() throw explicitly on NaN.

Round five found that "throw explicitly on NaN" was itself too narrow, and — more importantly — named why narrow fixes kept recurring. Number.isNaN(v) only rejects the literal float NaN; it does nothing for undefined, null, a string, a boolean, an array, or an object, every one of which Math.min/Math.max silently coerces into a number anyway — and undefined/null are exactly what a dropped JSON key or a NULL database column actually produce, not an exotic input. Separately, an anchor's own month field had received no repair at all, unlike its sibling fields — month: 0 and month: 12 ("December" twice, differently spelled) weren't deduplicated, silently reopening round one's original duplicate-month bug through a different door. Four rounds in, the reviewer's diagnosis was structural, not another missing case: "enumerate every malformed JS value and handle it inline is a search that doesn't terminate." Their recommendation — validate once, at the boundary, with the schema that already exists; let the evaluator trust the type completely, with zero runtime repair of its own — is what the rest of this section now describes, replacing the defense-in-depth version rather than patching it again.

interface SliderCurve {
  anchors: Anchor[];      // at least 1, MUST have unique months — see below.
                            // One anchor = flat, no season.
}

interface Anchor {
  month: number;           // 1–12
  value: number;           // 0–10, the value AT this month, exactly
  steepness?: number;      // 1–10. Default 2 (moderate). Governs how sharply
                            // the curve takes hold as it transitions
                            // TOWARD this anchor — see below.
}

Invariant: anchors must have unique months, and both value and steepness stay in range. Two anchors both claiming January isn't a curve shape, it's contradictory data — which value is January supposed to be? A zod schema already enumerates a type completely, in one declarative place — z.number() alone rejects NaN, undefined, null, strings, and booleans before .min()/.max()/.int() even run — which is more complete than any of the hand-rolled runtime guards that came before it, verified directly:

const anchorSchema = z.object({
  month: z.number().int().min(1).max(12),
  value: z.number().min(0).max(10),
  steepness: z.number().min(1).max(10).optional(),   // k < 1 rejected outright — see below
});

const sliderCurveSchema = z
  .object({ anchors: z.array(anchorSchema).min(1) })
  .refine(
    (c) => new Set(c.anchors.map((a) => a.month)).size === c.anchors.length,
    { message: 'Anchors must have unique months.' },
  );

The schema is necessary but not, on its own, sufficient — TypeScript's structural typing means any object shaped like { anchors: [...] } still satisfies the SliderCurve type whether or not it ever passed through the schema. Closing that gap needs one more thing: a type nothing can satisfy except by going through the parser.

declare const VALIDATED: unique symbol;
type SliderCurve = z.infer<typeof sliderCurveSchema> & { readonly [VALIDATED]: true };

function parseSliderCurve(raw: unknown): SliderCurve {
  return sliderCurveSchema.parse(raw) as SliderCurve;   // the only place this cast is allowed
}

That brand is what makes "validate once, trust everywhere after" actually true rather than aspirational: a plain object literal can't be passed where a SliderCurve is expected, so the only way to get one is parseSliderCurve — every place curve data enters the process (the admin save path, the migration script's output, and reading the sliderCurves column back out of the database) goes through it once, and curveValue/crowdsScore below do zero runtime repair of their own.

The evaluator: sort the anchors by month. For any given month, find the two consecutive anchors that bracket it (wrapping December to January). Compute how far between them this month sits, as a fraction from 0 to 1 — then instead of a straight line, ease that fraction through an S-curve before blending the two anchors' values. The steepness of that transition belongs to the anchor being transitioned toward — not an average of both. A peak's own steepness controls how sharply the curve rises into it; how sharply it falls away afterward is controlled by whichever anchor comes next. This is what actually makes the two sides of a peak independently tunable.

function ease(t: number, k: number): number {
  if (t <= 0) return 0;
  if (t >= 1) return 1;
  const a = t ** k, b = (1 - t) ** k;
  const sum = a + b;
  if (sum === 0) return t < 0.5 ? 0 : 1;   // extreme k underflows both branches
  return a / sum;                          // to 0 in floating point — round to the
}                                           // nearer side instead of dividing 0/0.

function normalizeMonth(month: number): number {
  // Real domain logic, not input repair: `month` is a runtime query parameter
  // (new Date().getMonth()+1), not persisted data the schema covers, so
  // wrapping it is a legitimate calendar operation, the same way "3 months
  // from November" legitimately means February.
  if (!Number.isFinite(month) || !Number.isInteger(month)) {
    throw new Error('month must be a finite integer');
  }
  return ((month - 1) % 12 + 12) % 12 + 1;   // 14 -> Feb, 0 -> Dec, -12 -> Dec: wrap, don't crash or drift
}

function curveValue(month: number, curve: SliderCurve): number {
  // curve is trusted completely: anchors.length >= 1, unique months,
  // value/steepness in range are all guaranteed by parseSliderCurve. No
  // dedup, no clamp, no NaN guard — that enumeration belongs in the schema.
  const queryMonth = normalizeMonth(month);
  const anchors = curve.anchors;
  if (anchors.length === 1) return anchors[0].value;
  const sorted = [...anchors].sort((a, b) => a.month - b.month);
  for (let i = 0; i < sorted.length; i++) {
    const A = sorted[i], B = sorted[(i + 1) % sorted.length];
    let spanAB = B.month - A.month; if (spanAB <= 0) spanAB += 12;
    let spanAm = queryMonth - A.month; if (spanAm < 0) spanAm += 12;
    if (spanAm <= spanAB) {
      const t = spanAm / spanAB;
      const k = B.steepness ?? 2;   // B, not avg(A, B) — see above
      return A.value + (B.value - A.value) * ease(t, k);
    }
  }
  // Impossible by construction: the spans above partition the full 12-month
  // circle, so some bracket always matches. An assertion about curveValue's
  // OWN correctness, not input repair — if it fires, the bug is in this
  // function, not the caller's data.
  throw new Error('curveValue: no bracketing anchors found — internal invariant violated');
}

One failure mode now, not two: bad data is rejected at parseSliderCurve, with a structured error naming the exact invalid field, before it can ever reach curveValue. There's nothing left inside the evaluator to "repair," because nothing invalid can get in — which is also why the function got shorter across this round, not longer: no clamp, no dedup Map, no per-field NaN handling. The query month is the one exception, and on purpose — it isn't part of the persisted SliderCurve the schema covers, so normalizeMonth validating and wrapping it is real domain logic, not defensive input repair, and stays. This is the actual implementation, not an illustration of one — src/lib/scoring/curve.ts, covered by tests/scoring/curve.test.ts, including property-based fuzzing of the schema boundary itself against every JS value shape (not just extreme numbers) that a dropped key or a NULL column can actually produce.

That's the whole engine — no separate baseline field, no decay radius, no per-anchor reach to tune independently of its neighbors. A flat interest is one anchor. A gradual season is two anchors with low steepness. A sharp spike is two anchors with high steepness. A season with a real plateau is three or four anchors. The same two knobs — where an anchor sits, and how steep the transition into it is — produce every shape below, including genuinely asymmetric ones (a fast onset, a slow fade): give the peak a high steepness and the following trough a low one, and the rise and fall are shaped completely independently.

Worked examples

The other cases you asked about all fall out of the same two knobs — where anchors sit and how steep the transitions between them are — without inventing anything new:

Avoiding Crowds and Low-Season Deals (their actual slider labels — see constants.ts) are the one case I'd deliberately not author this way — they aren't an activity with a season, they're a reflection of how busy everything else is. And they're the same reflection twice: the current formula computes both from one identical code path (destinations.ts's case 'deals': case 'crowds':) — a peak month scores low, a low-season month scores high, for both sliders at once. They're not inverses of each other; "good for avoiding crowds" and "a good deal" move together.

This one was wrong until checked against real data. An earlier draft of this formula computed a literal busyness score — peak season high, low season low — and derived deals as its 10-complement. That's backwards: "Avoiding Crowds" is a positive-framed slider, so a quiet month should score high, not low. Every synthetic worked example in this document still would have looked reasonable with the sign backwards, because they were built to demonstrate the mechanism, not to catch this. What caught it was Phase 3's parallel-diff audit (below) run against the real database: dozens of destinations — Raja Ampat, Bhutan, Madagascar, Ethiopia, Zimbabwe among them — showed the old formula's authored low season scoring 9-10 and this formula's first draft scoring ~2 for the identical months. Not floating-point noise; an inverted sign, found the same way rounds 1-5 found everything else in this document: by computing the real numbers and looking, just this time against production data instead of a hostile reviewer's constructed examples.

function seasonalQuietness(curves: Record<string, SliderCurve>, naSliders: string[], month: number): number {
  const queryMonth = normalizeMonth(month);
  const deviations: number[] = [];
  for (const [key, curve] of Object.entries(curves)) {
    if (naSliders.includes(key)) continue;
    const monthly = range(1, 13).map((m) => curveValue(m, curve));
    const min = Math.min(...monthly), max = Math.max(...monthly), spread = max - min;
    if (spread === 0) continue;              // flat slider carries no signal either way
    const avg = mean(monthly);
    deviations.push((monthly[queryMonth - 1] - avg) / spread);  // signed, fraction of THIS slider's own range
  }
  const avgDeviation = deviations.length ? mean(deviations) : 0;  // bounded to exactly [-1, +1] given valid inputs
  // A month running ABOVE its sliders' typical level is objectively busier —
  // and busier is WORSE for avoiding crowds and WORSE for a deal, hence the
  // minus sign. The clamp is a floating-point safety net (avgDeviation is
  // provably in [-1, 1] already), not input repair.
  return Math.min(10, Math.max(0, 5 - avgDeviation * 5));
}
function crowdsScore(curves: Record<string, SliderCurve>, naSliders: string[], month: number): number {
  return seasonalQuietness(curves, naSliders, month);
}
function dealsScore(curves: Record<string, SliderCurve>, naSliders: string[], month: number): number {
  return seasonalQuietness(curves, naSliders, month); // same signal, not an inverse — see above
}

Normalizing by each slider's own range (max − min), not its average, is what makes this safe to blend across 52 very different-shaped sliders — and it's a correction from an earlier draft of this formula, which divided by average instead. That version was never actually run against anything until round three of review did: dividing by a low average is unbounded on the upside (a sparsely-covered, spiky slider could report a deviation of several hundred percent), while a monthly value can't fall below 0, so the downside was capped at −1. That asymmetry let a single spiky slider on a lightly-tagged destination swing the whole score to its ceiling for months at a time. Dividing by range instead is symmetric by construction — monthly and the average both live inside [min, max], so the deviation can never exceed ±1 — which is what actually makes it safe for a wide-swinging slider like aurora (1 → 9) and a nearly-flat one like museums (8 → 8) to share one average without either dominating it.

Computed by the real implementation, not by hand, for this explicit four-slider set — aurora (Jul:1 → Jan:9, k2), museums (flat, 8), hiking (Jan:2 → Jul:9, k2), and a local festival timed to coincide with hiking's own peak (Jun:2 → Jul:10 → Aug:2, k8), chosen deliberately so the "several things peaking together reads as busy — and therefore worse for both sliders" effect is visible in the numbers below rather than averaged away:

A month where most interests are running well above their own typical level reads as objectively busier — that becomes the crowds score, mapped onto the usual 0–10 scale around a "typical month" of 5, and deals as its direct inverse. One formula, computed from data that's already there, instead of a 53rd curve a human has to separately author and keep in sync with the other 52 by hand.

04 · Consequence

What this removes, what stays

Removed entirely

  • The 10-branch formula switch (sun/swim/hiking/snow/culture/food/shopping/wildlife/birding/deals)
  • sliderCaps — nothing left to cap
  • sliderEvents as a separate mechanism — a second peak is just another anchor
  • dryMonths/wetMonths/hotMonths/coldMonths/peakMonths/lowMonths and 8 more month-flag arrays, as scoring inputs
  • peakIntensity / crowdBaseline, as scoring inputs
  • shopClosures as a cross-cutting flag — a real low-season dip is just that slider's own curve

Unchanged

  • seasonalHazards — a real, different concept: one authored risk discounting several unrelated sliders at once, not worth duplicating per-slider
  • naSliders — a slider is applicable or it isn't, orthogonal to its curve
  • scoreOverrides — still the highest-precedence, "just fix this one month" escape hatch
  • signatureTier / activityStyleTiers — identity and sub-style, not scoring math

The month-flag arrays don't necessarily disappear as data — "wet season: Jun–Aug" is genuinely useful as descriptive badge text on the destination page. What they stop being is a scoring input. Today the same flag has to be honest about two different jobs at once (drive the formula, drive the badge); splitting them means the badge text can say whatever's actually true without worrying it'll also nudge some unrelated slider's math.

05 · Storage

The data shape

One jsonb column replaces baseScores, sliderCaps, sliderEvents, and the 14 month-array columns:

sliderCurves: jsonb('slider_curves')
  .notNull().default({})
  .$type<Record<string, SliderCurve>>()

For a flat slider this is { anchors: [{ month: 1, value: 8 }] } — no bigger than today's bare baseScores.museumsArt = 8, and the month is irrelevant when there's only one. The data only grows where a destination genuinely has seasonal shape to describe, which is the honest place for that complexity to live.

Because the interpolated fill is already rendered live across all 12 months, the grid also doubles as the guard against the anchor-spacing trap below: two anchors landing a month apart is visible immediately as one abrupt cell next to eleven held-flat ones, not discovered later on a chart.

07 · Rollout

Migration

  1. 1
    Add the column, additive only. sliderCurves alongside every existing column — nothing reads it yet.
  2. 2
    Auto-derive curves from today's live output. For each destination × slider, take the current 12 computed monthly values (already correct, already battle-tested) and fit a sparse anchor set that reproduces them. deals/crowds are excluded — they're derived, not fitted (see section 03). Real algorithm, not a placeholder: greedy growth from the curve's global min/max month, fitting each arc's steepness by grid search, adding the single worst-error month as a new anchor until within tolerance — see src/lib/scoring/fitCurve.ts and tests/scoring/fitCurve.test.ts. Run against all 9,497 real non-N/A curves in the current database: every single one fits within half a point of the source (the tolerance that guarantees the same displayed integer), using a mean of 3.6 anchors — and only 18 curves (0.19%) needed every month as its own anchor to get there, all of them the same recognizable shape (a value alternating between three levels roughly twice a year, e.g. Budapest's scenicLandscapes: 0,0,4,4,7,7,4,4,7,4,4,0). This preserves every existing number exactly; it only changes the representation.
  3. 3
    Parallel-run and diff. New evaluator runs alongside the old formula; assert its output matches today's for all 200 × 53 — same gate this session already used for the places migration. Built and run: scripts/audit-curve-migration-parity.ts (npm run db:audit:curve-migration). Two genuinely different halves — every fitted slider curve (Part A) should match the old formula almost exactly, a pure correctness check; avoidingCrowds/lowSeasonDeals (Part B) are computed by a completely different formula now, so real disagreement there is expected, useful content-review signal, not a bug list. Part A: PASS across all 9,497 real curves, 0 discrepancies above tolerance. Part B is exactly what caught the sign-inversion bug described above — before the fix, 23.4% of month-level comparisons disagreed by 4+ points on the 0-10 scale; after it, 10.4%, and essentially all of the remainder traces to one further, still-open question: an inaccessible month (Ladakh's winter, Antarctica's off-season) forces every slider to 0 under the old formula, including crowds/deals, but the new derived formula has no equivalent override — a genuinely quiet, unvisitable month currently reads as a great month for avoiding crowds, which is true but probably not the intended framing. Added to Open Decisions below.
  4. 4
    Cut the live read path over. Old formula stays in the codebase, unused, as a same-day rollback.
  5. 5
    Editorial pass, separately. Only now does anyone go smooth out the real flat-plateau artifacts the audit script already flags (211 of them) — easy at this point, since softening a transition is just moving an anchor, not fighting formula internals.

08 · Still open

Open decisions

  • Whether month-flag facts (wet season, shop closures) get rebuilt as standalone badge content, or dropped if nothing currently reads them for that purpose.
  • Whether hazards multiply the curve value (today's behavior) or also get an anchor-shaped authoring option.
  • Whether seasonalQuietness needs an explicit override for a month nobody can actually visit. Found by Phase 3's real-data audit: an inaccessible month forces every slider to 0 under the old formula (including crowds/deals), but the new derived formula has no equivalent concept — it just sees every other slider sitting at its own low, which correctly reads as "quiet," so Ladakh's snowed-in winter and Antarctica's off-season currently score as some of the best months for avoiding crowds and finding a deal. Defensible in one sense (true, if you could get there) and misleading in another (you can't) — needs a product call, not a formula tweak, since the honest fix is probably "hide/gray out crowds and deals for a month the destination is inaccessible," not a math change.
  • Anchors placed close together still don't produce a "short hold" — they produce one short arc plus one long one covering the rest of the year. That's now visible live in the Place Profile grid rather than only discovered later (see the admin table above), which closes the "silent" part of this trap, but the exact threshold for an explicit inline warning (2 months apart? 1?) and its wording are still undecided.
  • Two independently-authored seasonal peaks close together on the calendar (e.g. two sliderEvents-equivalent bumps a month apart) haven't been checked against real data for the same fade/rise interaction the asymmetry fix above addresses — worth testing against actual destinations with double seasons before assuming it composes cleanly.
